二、为什么不能直接用时间戳做唯一 ID

时间戳虽然递增，但不能直接作为唯一 ID。

原因是高并发场景下，多个请求可能在同一时间到达：

  • 不同服务实例在同一毫秒生成 ID；
  • 同一服务实例在同一毫秒处理多个请求；
  • 如果 ID 只包含时间戳，就会重复。

Snowflake 不是固定模板，而是一种设计思想：

七、时钟回拨问题

1. 问题来源

Snowflake 依赖机器时间。

机器时间可能因为 NTP 校准发生回拨：

如果服务继续发号，就可能生成与 5 秒前相同时间段内的 ID，导致重复。

2. 解决思路

每次生成 ID 时，都要比较：

如果当前时间小于上一次时间，说明发生了时钟回拨。

处理方式：

回拨情况 处理策略
回拨时间较短 阻塞等待一小段时间后重试
回拨时间较长 直接拒绝请求，避免重复 ID
机器长期漂移严重 从服务集群中摘除该实例

也可以对 ID 生成器集群关闭 NTP 自动同步，避免运行中突然回拨，但需要额外监控时钟漂移。

这种架构的特点：

  • 多机房可并行发号；

  • 发号过程主要在本地完成；
  • 性能高，不依赖中心服务逐次分配；
  • 生成结果趋势递增，适合作为数据库主键。

九、核心架构思想

  1. 趋势递增比严格单调递增更适合分布式高并发系统。
  2. 时间戳适合放在 ID 高位，用来保证整体递增趋势。
  3. 不能直接用时间戳做唯一 ID，必须加入实例和并发序列信息。
  4. Snowflake 的本质是按位编码，把多个变量压缩进 64 位整数。
  5. 位数分配应根据业务容量灵活调整，而不是死套经典模板。
  6. Worker ID 必须全局唯一，否则多实例会生成重复 ID。
  7. Worker ID 可以通过数据库自增主键、etcd 或 ZooKeeper 分配。
  8. 同一毫秒内的序列号决定单实例瞬时发号能力。
  9. 时钟回拨是基于时间戳发号的核心风险，必须检测并处理。
  10. Snowflake 用局部有序换取高并发、高可用和水平扩展能力。

十、一句话总结

基于时间戳的趋势递增唯一 ID 通过 Snowflake 类算法，把相对时间戳、机房 ID、Worker ID 和毫秒内序列号编码进 64 位整数，从而实现多机房、多实例的高并发本地发号；它牺牲严格全局单调递增，换来了更好的分布式扩展能力，但必须解决 Worker ID 分配和时钟回拨问题。
