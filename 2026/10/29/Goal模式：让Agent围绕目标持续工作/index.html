以 Codex 的 Goal 为例，它不只是让 Agent 持续执行的一段提示词，而是附加在当前线程上的持久目标状态。它记录要达成什么、如何验证完成，以及任务目前处于什么状态；Codex 再根据每轮产生的证据和线程状态，决定是否继续，直到目标完成或进入暂停、预算受限、阻塞等状态。

理解 Goal 模式，可以更清楚地看懂 AI Agent 是怎么把大任务拆成小步骤、如何验证自己的工作，以及什么时候应该停下来。

一、普通对话和 Goal 模式有什么区别

普通对话通常是一问一答：用户发出一条指令，模型完成当前任务，然后停下来等用户继续安排。

每一轮都需要用户接力。用户得检查结果、补充要求，再告诉它下一步做什么。任务越长，用户参与的次数就越多。

Goal 模式则围绕一个持续目标运行：

用户在开始时定义目标，在最后验收结果。中间由 Agent 自己完成一轮、检查一轮，再判断要不要继续。

简单来说，普通对话需要用户安排每一步，Goal 模式让 Agent 围绕一个目标持续推进。

二、外面套一个循环，能不能代替 Goal 模式

了解到区别后就可能有一个直觉：在普通模式外面写一个循环，把固定提示词和历史对话反复发给模型，等它说“完成”就停。这样看起来也能让 AI 自动执行。

但如果只是简单地重复发送提示词，它和 Goal 模式之间还有几处差别。

1. 暂停和恢复不容易管理

任务运行过程中，用户可能想暂停、修改目标，或者补充预算。一个只负责反复发送提示词的循环，不一定知道当前任务走到哪里，也不一定能安全地停下来再恢复。

如果还要管理这些状态，外层程序就得另外记录进度、预算和恢复位置。做到这一步，它就不只是简单的循环了。

2. 验证不能只靠一句“检查一下”

如果提示词只写“完成后检查一下”，模型未必知道该检查什么，也可能把“看起来没问题”当成验证通过。

更标准的做法是把验证标准写成具体证据：搜索结果应该为空，测试应该通过，构建应该成功。Goal 会要求 Codex 在判断完成前核对相关证据；具体是否每一轮都运行同一组检查，要看目标怎么写以及当前工作需要什么，而不是 Goal 机制自动保证每轮都执行固定测试。

3. 大任务需要拆成可验证的小步

如果所有事情都堆在一个很长的执行过程中，任务范围容易失控，失败时也很难定位问题。

Agent 通常会把大任务拆成较小的工作单元，方便检查进度和定位问题。每轮的工作量并非由 Goal 预先固定；它会根据已经发现的情况选择下一步，再根据结果决定是否继续。

外部系统当然也可以实现暂停恢复、状态管理和逐轮验证。但那时它构建的已经是一套长任务管理机制，而不只是一个简单循环。

三、用老板和员工来理解 Goal 模式

把 Goal 模式想象成老板给远程员工安排一项长期任务。

老板告诉员工最终要达到什么结果，并给出预算。例如：

把销售额从 30% 提升到 50%，预算用完前持续推进。

老板不需要每天安排员工做什么，也不需要逐项了解每天的进展。员工根据目标安排工作，同时有财务监控预算。预算用完时，任务就暂停下来，等待老板补充预算或调整方向。

这个例子里，老板关心的是最终目标、预算，以及什么时候应该停下来。

Goal 模式也类似：用户更关注目标有没有达成，以及 Agent 是否还有资源继续推进，而不需要亲自安排中间的每一个动作。

四、区分 Plan 模式和 Goal 模式

可以把 Plan 模式理解成“先想好怎么做”，把 Goal 模式理解成“围绕目标持续做到完成”。

模式 我关注的问题
Plan 接下来应该按什么步骤做？
Goal 怎样持续推进，并确认最终目标已经达成？

Plan 可以提前看到 Agent 打算怎么做，也方便用户在开始前调整方案。但有了计划，不代表任务会自动连续执行很多轮。

Goal 更关注执行和验证的闭环。如果目标还没完成，Agent 会根据前一轮的结果继续做；如果已经满足完成条件，它才会结束。

实际处理复杂任务时，可以先用 Plan 理清思路，再把明确的最终目标和验证标准交给 Goal 模式持续执行。在 Codex 中，单纯的 Plan-only 工作不会触发 Goal 自动续跑；计划本身不是持续执行的信号。

五、Codex Goal 的底层逻辑

从 OpenAI 公开的架构说明看，Codex Goal 由几部分配合完成：线程级目标状态、正常的 Agent 执行轮次、轮次结束时的续跑调度，以及基于证据的完成判断。它不是另一个模型，也不是一个不带状态管理的 while 循环。

1. 目标状态保存在当前线程

创建 Goal 后，目标会作为持久状态附加到当前线程。状态包括目标内容、生命周期、预算和进度信息。它不是全局记忆，也不是项目级指令；它与当前线程中的上下文关联，例如已经检查过的文件、运行过的命令、产生的改动和日志。

2. 每一轮仍然是正常的 Agent 工作

Goal 不会直接替模型完成任务。每一轮还是由 Codex 根据目标和当前上下文进行分析，再按需调用工具、修改文件、运行命令并读取结果。Goal 的作用是让长期目标在多轮之间保持有效，而不是预先指定所有步骤或轮数。

3. 轮次结束后由调度器判断是否续跑

当前轮结束后，Codex 不会无条件立即开启下一轮。调度器会检查是否到了安全的续跑时机：Goal 仍处于有效状态、预算尚可用、线程已经空闲、没有排队的用户输入，也没有其他待处理工作。条件满足时，系统才会准备下一轮；如果用户打断任务，续跑会暂停。

续跑是事件驱动的：它发生在轮次结束等安全边界，而不是模型在一个回合里不停地自我调用。为了避免空转，如果自动续跑的一轮没有调用任何工具，系统也会抑制紧接着的下一次自动续跑。

4. 续跑提示会重新强调目标和证据

满足续跑条件后，Codex 会在下一轮提示中带上当前 Goal，让模型继续围绕同一个终态工作。模型再结合线程里的最新上下文和工具结果选择下一步。

当它准备宣布完成时，需要把目标和具体证据对照起来，例如检查文件、测试结果、日志、基准数据或生成的产物。预算用完不等于完成；如果证据不足或遇到阻塞，就应该停下来总结进度和所需输入。

公开说明描述的是基于提示和工具结果进行证据审计，没有说每轮都会另外启动一个独立的“验证 Agent”。因此，测试、搜索和构建等检查要在 Goal 中写清楚；不能只凭“Goal 会自审”就假定每轮一定运行了某个固定验证流程。

六、把 Goal 的运行过程拆成几步

下面这张图把 Goal 从创建、执行和证据核对，到续跑、完成或暂停的流程放在一起。接下来我按步骤展开。

1. 用户先主动创建目标

Goal 是一种长程任务。用户需要明确选择目标模式，或者明确告诉工具要创建一个 Goal，而不是期待 Agent 根据普通需求自行推断。

这样可以避免一个普通问题被误解成长时间运行的任务。

2. Agent 开始一轮工作

目标创建后，Agent 会读取目标和当前项目状态，选择当前最有价值的下一步。

例如，用户想把整个 src/ 目录从 CommonJS 迁移到 ESM，Agent 可以先处理一组关系简单的文件，再根据结果继续；也可能先调查迁移边界或依赖关系。具体怎么拆分由当前情况决定。

3. 按目标要求收集验证证据

Agent 按照 Goal 中定义的验证标准收集证据。对于 CommonJS 迁移，可以要求每批修改后都：

  • 搜索目标范围内是否还有需要迁移的 CommonJS 写法；
  • 运行项目测试；
  • 执行构建。

如果这一轮的检查失败，Agent 可以继续修复并重新运行相应检查。对于其他 Goal，验证频率和具体命令也应由任务的风险与目标来决定。

4. 根据目标和续跑条件决定下一步

每轮结束后，Codex 会根据目标和已获得的证据判断任务是否完成。如果目标已经满足，就结束；如果还没完成且续跑条件满足，就进入下一轮；如果用户输入排队、预算耗尽或遇到阻塞，就暂停续跑并等待处理。

每一轮的结果和摘要会成为后续工作的上下文。这样任务虽然分成多轮，但目标和进度不会从头开始。

5. 遇到停止条件时由用户处理

Goal 不会在任何情况下都一直运行。它可能在以下情况结束或暂停：

  • 目标已经达成；
  • 遇到无法自动解决的阻塞；
  • 预算或套餐额度耗尽；
  • 用户主动停止任务。

如果预算耗尽，或者遇到必须由用户决定的问题，就需要补充预算、调整目标或亲自处理阻塞。暂停、恢复和清除目标等生命周期操作也由用户或系统控制。

七、在目标提示词里该写哪些内容

在写 Goal 提示词时，要优先把两件事说清楚：最终要得到什么结果，以及用什么证据证明结果已经达成。

如果任务比较复杂，还要补上范围、循环方式和停止规则。

要素 我会说明什么 是否建议必写
终态 最后应该得到什么结果？ 必写
证据 如何证明结果已经达成？ 必写
边界 允许修改哪些内容？ 视任务而定
循环方式 每轮做什么、检查什么？ 视任务而定
停止规则 遇到什么情况需要停下来？ 视任务而定

1. 终态：想要的最终结果是什么

“把项目改好”太模糊，Agent 不知道什么才算好。

推荐把目标写具体一些：

将 src/ 目录中目标范围内的 CommonJS 模块迁移为 ESM，并保持现有功能不变。

2. 证据：怎么知道它真的完成了

可以把完成条件写成可以实际执行的检查：

  • 在指定范围内搜索需要迁移的 require、module.exports 等写法，确认没有遗留；
  • 项目测试全部通过；
  • 项目构建成功。

如果只说“检查一下”，Agent 可能只给一个主观判断。写清楚证据后，完成状态才更容易复核。

3. 边界：允许它改哪些地方

例如，可以规定只修改 src/ 中的业务文件，不改构建配置、依赖版本和测试框架。

边界越清楚，越不容易遇到不相关的改动。

4. 循环方式：希望它怎么分批推进

可以要求 Agent 每轮迁移一批文件，每批完成后重新搜索、测试和构建。这样每一轮的工作量比较可控，失败时也更容易定位。

5. 停止规则：什么时候需要它停下来

例如，遇到动态加载、特殊运行时变量，或者无法确认语义的模块时，可以要求它记录文件和原因并报告，不要为了让搜索结果归零而强行改写。

八、如何写 CommonJS 迁移的目标

如果要把前端项目 src/ 目录里的 CommonJS 迁移为 ESM，可以这样写：

目标： 将前端项目 src/ 目录中目标范围内的 CommonJS 写法迁移为 ESM，并保持现有功能不变。
验证： 每轮修改后，在目标范围内搜索需要迁移的 CommonJS 写法；运行项目测试；执行构建。三项都通过后，本轮才算完成。
范围： 只修改 src/ 目录中的目标文件，不改无关配置、依赖版本和测试框架。
迭代方式： 每轮迁移一小批文件，完成后重新搜索并运行测试和构建。根据上一轮结果选择下一批文件。
停止规则： 遇到无法确认语义的模块或无法自动迁移的写法时，记录文件和原因并报告，不要强行绕过。

这样明确说出了终态、证据、边界、循环方式和停止规则。

如果某轮测试失败，则希望 Agent 先定位并尝试修复，再重新验证；如果遇到目标里定义的阻塞条件，就停下来告诉用户，而不是为了继续执行而随意猜测。

九、总共会运行多少轮，开始时并不知道

很容易一开始以为，创建 Goal 时模型会先估算总共需要多少轮，然后按这个轮数执行。但实际流程不是预先算好轮数，再机械地跑完这些轮次。

Agent 会在每轮开始时根据目标和现有进度判断下一步；轮次结束后，Codex 再依据证据和调度条件决定完成、暂停还是续跑：

所以，一个任务最终会有多少轮，开始时可能并不知道。例如这个 Goal 已经执行了一天十二小时，在这段时间里，每轮都会继续参考之前的进度，完成一部分工作后做验证，再总结这一轮的结果。

可以把 turn 理解为一个有开始、有结束、能验证的小工作单元，而不是预先固定数量的对话轮次。直到最终一轮判断所有目标和验证条件都已满足，任务才算完成。

十、哪些任务适合使用 Goal

要把 Goal 用在目标清楚、可以拆成小步、每步又有办法验证的任务里，例如：

  • 批量迁移代码，并用搜索、测试和构建确认结果；
  • 跨多个模块的重构，要求每轮保持测试通过；
  • 清理一组范围明确的技术债；
  • 按固定标准持续处理一批文件或数据。

如果需求还没想清楚，或者中间有很多需要用户做的产品决策，不要急着交给 Goal 长时间运行。可以先通过普通对话把问题澄清，或用 Plan 讨论方案，再决定要不要创建目标。

结语

Goal 模式不是让 AI 无止境地工作，而是让 Agent 围绕一个明确目标形成执行闭环：

做一轮、验一轮、看进度，再决定继续还是结束。

写目标时，要重视终态和证据；任务比较复杂时，再补充边界、循环方式和停止规则。这样 Agent 每一轮更容易产出可检查的结果，也不容易在长任务里偏离方向。

最终要关心的不是它跑了多少轮，而是每轮有没有完成一块可验证的工作，以及最后有没有用明确的证据证明目标已经达成。
