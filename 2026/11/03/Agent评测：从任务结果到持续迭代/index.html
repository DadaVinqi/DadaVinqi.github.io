评测一个 Agent，需要回答三个问题：它有没有完成任务，执行过程是否可靠，以及完成任务的成本和时间是否可接受。

这三个问题分别对应端到端评测、轨迹评测和运行表现评测。把它们放在一起，才能看清一个 Agent 能做什么、为什么失败，以及是否适合稳定地投入使用。

落地时，还需要准备可复现的任务用例，为具体业务定义成功标准，并用一套可复用的评测系统，把执行、记录、评分和版本比较连接起来。

一、评测对象是完整任务

普通问答通常可以围绕输入和回答进行评测。Agent 则会调用工具、改变外部状态，还可能跨越多轮执行。因此，评测需要覆盖模型、提示词、检索、工具和运行框架共同完成的任务。

以客服退款 Agent 为例，用户提出请求后，它需要查询订单、理解退款规则、判断是否满足条件，并在获得必要授权后提交退款。

如果它回复“退款成功”，但系统里没有生成退款记录，任务就没有完成。如果订单不符合退款条件，准确说明原因并给出合适的后续处理方式，也可以是一次成功的执行。

这要求我们在测试开始前明确：什么状态才算完成，用什么证据证明完成。

对于报告生成任务，证据可能是文件、内容覆盖度和事实准确性；对于代码修改任务，可能是功能行为、测试结果和构建状态；对于业务操作任务，则需要核对系统中的实际记录。

二、从三个维度观察 Agent

1. 端到端评测：任务有没有完成

端到端评测从任务入口出发，检查最终结果是否满足要求。它可以把内部执行过程视为黑盒，但必须验证可观察的产物和状态变化。

在退款场景中，需要检查订单是否正确、金额是否准确、实际处理状态是否符合规则，以及回复是否与处理结果一致。

最基础的指标是任务成功率：

复杂任务还可以记录部分完成情况。例如，正确查询了订单和规则，但没有完成退款提交。这些信息有助于诊断，不过应与整体成功率分开，避免把“完成了大部分步骤”当成“任务已经成功”。

2. 轨迹评测：执行过程是否可靠

端到端结果能告诉我们哪些任务失败，轨迹则帮助解释失败发生在哪里。

同一个退款任务，Agent 可能一次完成，也可能反复查询同一订单、调用无关工具，甚至在超时后重复提交。这些差异会影响可靠性和成本。

轨迹评测依据可记录的计划、工具调用、参数、返回结果和中间状态，检查：

  • 是否选择了适合当前任务的工具，参数是否正确；
  • 是否依据查询结果作出判断，关键操作是否满足前置条件；
  • 遇到失败后，是否合理重试、调整方法或停止；
  • 是否出现无效循环、重复操作或未经验证就宣布完成。

工具调用成功不等于调用正确。接口返回成功，但订单号或退款金额错误，依然是严重问题。

轨迹评测也需要允许多种合理路径。Agent 可以先查订单，也可以先查规则，只要满足必要的依赖和约束，就不应因为步骤与参考路径不同而被判错。

对于跨多轮执行的 Agent，还要检查它是否保留了原始目标和约束、中断后能否恢复，以及历史摘要是否准确记录了尚未完成的工作。

3. 运行表现评测：能否稳定、经济地使用

一个能够完成任务的 Agent，仍然可能因为响应过慢、重试过多或成本过高而难以使用。

维度 需要观察的内容
延迟 首次响应时间、任务总耗时、P50/P95 耗时
成本 模型调用、工具调用和重试产生的费用
稳定性 重复执行的成功情况、超时率、异常恢复情况

P95 耗时表示约 95% 的任务能在这个时间内完成，适合观察较慢请求的体验。对于长任务，任务总耗时尤其重要：很快回复“开始处理”，并不代表很快完成了任务。

成本也需要结合成功率观察。一个每次运行很便宜、却经常失败的 Agent，实际使用成本可能更高。可以统计：

这个口径把失败和重试的开销一起计入，更接近完成实际工作的代价。

安全与权限边界则应贯穿三类评测：既检查是否发生了未授权的状态变更，也检查执行过程中的敏感信息处理和工具使用行为。

这些指标需要分别呈现。结果正确、过程可靠、成本可接受是不同要求，一个平均总分容易掩盖其中的短板。

三、不同 Agent，需要定制什么

定制评测，首先要围绕 Agent 的业务职责、使用环境和错误代价展开。

Agent 类型 主要任务 关键验收内容
客服 Agent 查询信息、解释规则、处理业务 问题是否解决、操作是否正确、解释是否符合规则
编程 Agent 实现功能、修复缺陷 功能是否生效、测试是否通过、原有能力是否退化
研究 Agent 收集资料、分析并生成报告 事实是否准确、证据是否可靠、关键问题是否覆盖
日程 Agent 查询时间、协调并创建会议 时间和参与人是否正确、是否冲突、日历是否实际更新

这些 Agent 都可以统计任务成功率，但判断成功的方法不同。编程任务可能通过功能测试验收，研究任务需要核对事实与证据，日程任务则要检查日历中的实际事件。

因此，需要定制的是任务用例、初始环境、业务约束、评分逻辑和通过要求。退款金额错误和报告遗漏一个次要观点，错误代价不同，相应的通过条件也需要分别制定。

同类 Agent 可以共享评测集。比较两个面向同一场景的实现时，应让它们执行相同任务，使用可比的工具权限、环境和预算，并采用一致的评分标准。跨场景的成功率应结合任务组成理解，不能仅凭数值高低判断哪个 Agent 更强。

四、怎样准备可复现的评测用例

1. 从实际任务收集素材

可以先列出 Agent 承担的任务类型，再从三个来源收集素材：

  • 日常验收任务：开发和发布前经常手工检查的功能；
  • 真实用户请求：代表实际使用频率、表达方式和任务难度的需求；
  • 历史失败案例：答错、工具用错、重复操作、中途停止等问题。

初期可以先整理二三十条高价值任务，用来发现明显的能力缺口和退化。随着问题变细、版本差异变小，再增加样本和重复运行次数。少量用例适合起步，其结果需要结合覆盖范围和波动解释。

2. 让每条用例具备完整信息

Agent 的评测数据通常需要包含用户目标、初始环境、可用工具、业务约束、预期终态和检查方法。

例如，一条退款用例需要提供订单状态、付款金额、适用规则和授权情况，并明确执行后应出现什么记录。只有问题和一段标准答案，无法完整验证这类任务。

字段 要写清楚的内容
编号与版本 如何定位用例，输入或标准发生了哪些变化
用户请求 用户实际会表达的需求，包括必要的后续对话
初始环境 已有数据、业务状态和执行身份
工具环境 可用工具、返回数据，以及需要注入的故障
业务约束 必须满足的条件和不允许发生的行为
预期终态 执行结束后应该留下的结果和状态
检查方法 每项要求怎样判定，哪些必须通过
标签 任务类型、主要风险、难度和数据集用途

初始数据应通过正常的工具或上下文提供给 Agent。预期终态、参考答案和评分逻辑由评测系统保存，避免把验收答案直接放入执行上下文。

3. 写出一条完整用例

下面是一条退款用例。业务规则和退款处理为演示而简化：测试工具在提交成功时同步生成成功记录，执行发生在隔离的测试环境中。

这份描述还需要由测试环境和评分器实现。例如，“其他订单状态保持不变”可以通过执行前后的快照比较；退款金额和记录数量可以直接查询测试数据库。用例中的自然语言条件应逐项对应到实际检查。

4. 扩展场景，覆盖失败风险

以正常用例为起点，每次改变一个关键条件，更容易判断 Agent 在哪类情况下出错。

场景 改变的条件 预期行为
正常完成 满足条件且用户已确认 正确提交一次退款
不符合规则 按本例规则，订单已发货 说明原因，不提交退款
已经处理 订单已完成退款 说明当前状态，不重复提交
信息不足 未指定订单，且存在多个候选订单 询问必要信息，不猜测目标
仅咨询 用户只问“能不能退” 查询并解释，不直接提交
查询失败 订单查询工具暂时不可用 按重试策略处理，不编造查询结果
提交结果不明 后台写入成功，但工具返回超时 核验状态，避免重复退款
用户改变要求 在提交前取消退款 停止提交，并准确说明处理状态

故障场景要写清楚触发条件。例如，“提交超时”需要区分操作根本没有发生，还是操作成功但响应丢失。两者在 Agent 看来可能相似，测试环境中的状态和正确恢复方式却可能不同。

用户中途取消的用例，也要明确消息在什么时机送达，例如“查询订单之后、提交退款之前”。固定这个时点，才能稳定复现测试。

给每条用例标记一个主要评测点，再逐步增加多个条件组合的复杂任务。这样既便于归因，也能检验真实场景中的连续决策能力。

5. 检查用例质量并组织数据集

用例正式入库前，可以先人工走通任务，再试跑 Agent，检查环境能否重置、规则是否明确，以及有效解法能否被正确判定。两名评审对同一结果经常产生分歧时，应先修订任务描述和评分标准。

按用途，可以把用例组织为三类：

数据集 作用
黄金集 经过专家确认，任务要求和评分依据清楚，提供可信基准
回归集 覆盖已经具备的能力，防止修改破坏原有功能
挑战集 覆盖复杂任务、边界情况和当前希望提升的能力

这三类可以重叠。一条由专家确认、来自线上故障的用例，既可以属于黄金集，也可以长期保留在回归集中。挑战用例被稳定解决后，也可以转为回归用例。

对于检索和外部工具，应保存必要的数据版本或测试快照，保证失败能够复现。相似问法和同一案例的简单变体，也应放在同一数据划分中，减少调优集与保留测试集之间的信息泄漏。

五、标准要能被稳定执行

评分方法可以组合使用程序检查、模型裁判和人工复核。

**能够明确验证的内容，优先交给程序。**例如金额是否一致、记录是否生成、文件是否存在、测试是否通过。这类检查速度快，也便于复现和定位错误。

**需要语义理解的内容，使用有明确细则的模型裁判。**例如解释是否清楚、结论是否有依据、是否遗漏必要信息。评分细则也就是 Rubric，需要为每个维度写出通过条件和典型错误。

以“退款解释是否完整”为例，可以检查回答是否说明处理结果、是否给出对应原因，以及是否在需要时提供下一步操作。相比直接要求“打一个零到十分”，这些条件更容易保持一致。

对于前面的正常退款用例，可以进一步规定：订单、金额和处理状态都必须与实际记录一致；用户没有额外操作要做时，无须为了“完整”而编造下一步。证据不足时，裁判应标记无法判断并转交复核。

**人工负责确认标准、校准裁判和复核争议。**人工之间也可能存在分歧，需要通过独立标注和评审统一口径。模型裁判与人工判断经常不一致时，应先检查评分细则和裁判可靠性，再解释 Agent 的分数变化。

对于错误订单、错误金额、未授权操作等关键问题，应单独设置必要通过条件，避免被其他维度的高分抵消。

六、可复用的评测框架包含什么

三类评测描述了观察 Agent 的视角。真正把测试跑起来，还需要一套负责执行、记录、评分和比较的系统，通常称为评测 Harness。

它与支撑 Agent 日常工作的运行框架职责不同：评测 Harness 在测试环境中调用被测 Agent，并收集证据、执行验收。

这套系统的很多能力可以复用，具体业务通过配置、适配接口和评分器接入。

模块 可以复用的能力 需要按 Agent 定制的内容
用例管理 存储、标签筛选、数据划分和版本管理 具体任务、初始数据和预期结果
环境管理 初始化、重置、快照保存和故障注入机制 业务数据、工具实现及故障触发条件
测试运行器 批量执行、并发、重复运行和超时控制 如何启动和调用目标 Agent
轨迹采集 统一记录调用、参数、返回结果和时间 如何接入 Agent 的日志或事件
评分执行 调用程序检查、模型裁判和人工复核流程 断言、评分细则及必要通过条件
指标与报告 汇总结果、展示失败、比较版本和检查阈值 成本口径、通过要求和业务分组

例如，评测编程 Agent 时，框架准备代码仓库、接收修改产物，再执行功能测试。评测退款 Agent 时，框架准备订单数据、接收操作记录，再核对退款状态。调度、记录和报告机制可以共用，环境准备与验收逻辑分别接入。

接入一个新的 Agent，通常需要先完成三件事：准备可重置的测试环境；让运行器能够传入任务并收集输出、轨迹和产物；把每项完成条件连接到相应的评分器。

**成功率的统计公式可以复用，什么情况算成功需要由具体任务定义。**框架也应明确区分任务失败、运行异常和评分异常，让读者能判断低分来自 Agent 行为，还是测试本身没有正常完成。

计划内的工具故障仍应按用例评估 Agent 的恢复行为。评测设施故障或评分失败则需要单独报告并处理，不能静默丢弃这些尝试。

七、先做离线比较，再观察真实流量

离线评测使用预先准备的任务集，适合在修改提示词、模型、检索策略或工具逻辑后比较效果。

首先运行当前版本，建立基线；再让新版本执行相同任务，比较成功率、轨迹问题、成本和耗时。每次运行应记录数据集、模型、提示词、工具和评分器的版本，防止多个因素同时变化，导致结果无法解释。

不同尝试应从一致、隔离的初始环境开始，避免上一次留下的记录影响下一次结果。关键任务需要重复运行，观察波动，不能只选择最好的一次。

在线评测面向真实流量，可以通过灰度发布、A/B 测试和生产监控观察实际效果。比较对象既可以是提示词，也可以是模型、检索方案或完整工作流。

线上既要看任务成功率，也要观察用户是否反复改写问题、是否需要转人工，以及成本和延迟是否变化。不同任务类型应分别统计，避免总体平均值掩盖某类场景的退化。

八、从指标下降追到具体原因

“退款没有完成”只是现象。订单查错、规则理解错、接口不可用，以及操作成功后没有正确核验，分别需要不同的修复。

可以从端到端结果出发，沿着轨迹逐步定位，再检查相关组件：

现象 优先检查的方向
缺少关键资料 数据是否存在、检索是否召回、上下文是否完整
工具参数错误 实体提取、字段映射、工具说明和参数校验
反复调用相同工具 返回结果是否可理解、重试策略和停止条件
已执行但结果不正确 状态变更、幂等处理和执行后的核验
很快宣布完成却没有证据 完成标准、证据收集和完成判定机制

归因时还要检查任务和评分器本身。环境异常、标准含糊，或者评分逻辑拒绝了有效解法，都可能造成低分。

九、让失败案例进入下一轮评测

线上发现问题后，应保留必要的环境和执行记录，将它整理成可复现的任务用例，明确失败原因和预期行为。修复之后，既要验证这条用例，也要运行相关回归集，检查改动是否影响原有能力。

当离线结果达到事先约定的要求，再逐步灰度，继续观察真实任务的成功率、延迟、成本和异常情况。出现明显退化时回滚，并把新问题带回评测集。

随着线上任务变化，还需要定期补充新的场景，检查原有数据是否仍有代表性。同时保留一部分未参与调优的测试任务，用来判断改进能否推广到新的情况。
